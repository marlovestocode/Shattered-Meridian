# Core Gameplay Foundation — Architectural Audit

**Date:** 2026-07-28
**Scope:** full `src/` tree — 162 Luau files, 42,351 lines
**Method:** four specialist domain audits (architecture, combat, movement/physics, performance),
reconciled and independently spot-verified against source. Every claim below carries a
`file:line` citation and was checked by reading the cited code, not inferred.

**Status of numbers:** counts are exact (derived from source + `Constants.lua`). Anything labelled
*projected* is a count multiplied by a cost model and is **not** runtime-profiled — no Studio
session was run. Converting projections into measurements is the instrumentation plan in §7.

---

## 1. Executive summary

The repository is two codebases sharing a name.

| Layer | State |
|---|---|
| Combat, movement, hit detection, FX, UI, player data | ~15k lines, production-grade, 403 test cases, exceptional comment discipline |
| Progression, Qi, abilities | **17 empty stub modules** |

The combat half is genuinely well engineered: one Heartbeat, one hitbox engine,
server-authoritative throughout, deterministic overlap queries (never `.Touched`), and comments
that explain *why* rather than *what*. It does not need rescuing. It needs targeted defect fixes
and two structural extractions before it can carry abilities.

The progression half does not exist. `software-architecture.md` documents it in full as though it
were live; that document describes the intended end state, not the repository.

**The single most consequential finding for planning:** work described as "improve the existing
Qi/progression/ability system" is greenfield construction of three systems, each comparable in
size to the combat layer that already exists.

### Verified state of the stub layer

17 modules are `function X.Init(): () end` with a header comment and nothing else:

`ProgressionSystem` · `MeridianSystem` · `TierSystem` · `BloodlineSystem` · `ArtSystem` ·
`AbsorbSystem` · `RewardSystem` · `AchievementSystem` · `QiDeviationSystem` · `AwakeningSystem` ·
`TerritorySystem` · `WorldSystem` · `RivalrySystem` · `BountySystem` · `FactionManager` ·
`ArtTreeManager` · `BloodlineManager`

`Main.server.lua:44-161` contains ~110 lines of dependency-ordering commentary — "Meridian XP is
the resource TierSystem's tier-up checks read", "Tier before bloodline/art" — describing the boot
order of fourteen functions that all do nothing. Those orderings have never once been exercised,
so they are untested assertions, not established facts.

**Qi does not exist server-side.** `ClientState.lua:81` renders `Qi = scope:Value(100)` — a
hardcoded HUD default with no owning system. **No ability or art system exists in any form.**

## 3. Confirmed defects

Ordered by severity. Every one independently verified against source.

### 3.1 Blocking gameplay defects

**D1 — Air-tech strands the player permanently limp.**
`RagdollController.lua:695-709`.
`RecoverJointsOnly` destroys constraints and clears `active[character]` without restoring the
`savedPlatformStand` / `savedAutoRotate` / `GettingUp` values captured at `:265-270`. Those values
are discarded with the entry. `HoldAloft` → `enterRigidHold` (`:94`) then re-snapshots
`PlatformStand`, reading `true`, and `exitRigidHold` (`:120`) faithfully restores `true`.
**Result: after a successful air-tech the player cannot walk until they die or an admin runs
`ResetCombatState`.** The `ChangeState(GettingUp)` at `:124` cannot override a true `PlatformStand`.

**D2 — Air-combo victims 2 and 3 have zero counterplay.**
`Constants.lua:1869` — `DashPunch.MaxTargets = 3`.
Both weapon Finishers use `MaxTargets = 1` with an explicit comment that a launcher commits to one
foe. DashPunch *is* a launcher. Because `airComboTarget` is a single field overwritten per victim
(`AirCombo.lua:191`) and `findAirComboAttacker` (`CombatSystem.lua:2484`) matches only that one
tracked target, the second and third victims are ragdoll-pinned 12 studs up for 1.8 s, cannot
block, parry, dash or slide, and their air-tech returns `"NotJuggled"`. Total helplessness.
**One-number fix, no dependencies.**

**D3 — Slide and dash survive being hit.**
`Movement.lua:198-223`.
The Dash and Slide tiers are evaluated *above* `hitSlowExpiry`, and `stunExpiry` /
`postureBrokenExpiry` / `ragdollExpiry` are consulted **only inside the Sprint branch**. Verified:
nothing outside `resetTransientCombatState` and `setActiveAction` ever clears `slideWindowExpiry`
or `dashWindowExpiry`. Press Slide, get hit 0.1 s later, and `ComputeDesiredWalkSpeed` still
returns `base * 2.0` for the remaining window. `HitSlowMultiplier` is documented as "the can't just
run away factor" and is currently defeatable on reaction. Reordering is insufficient — the windows
must be force-*ended*, or they resume after the slow lapses.

### 3.2 Mechanics that do not work as authored

**D4 — Primary can never throw Heavy2.**
`Constants.lua:2360` (`Heavy1.Cooldown = 3.00`) vs `:1532` (`ComboResetSeconds = 1.5`).
Throw Heavy1 at t=0 → `comboExpiry = 1.5`, `comboIndex = 1`. The cooldown blocks the next Heavy
until t=3.0. At t=3.0 `resetHeavyComboIfLapsed` (`CombatSystem.lua:720`) sees `3.0 > 1.5` and
zeroes `comboIndex`, so `nextComboIndex` is always 1. Heavy2 (21 dmg / 25 posture) is dead data.
Secondary is unaffected (`DaggerHeavy1.Cooldown = 0.58 < 1.5`), producing a silent, undocumented
power asymmetry between the two weapons.
Related: `MaxComboStacks = 5` clamps via `math.min` (`CombatSystem.lua:1758`); with a 2-stage array
a saturated counter would lock out Heavy2 a second way. Wrap, don't clamp.

**D5 — The Normal finisher variant's extra stun is a no-op.**
`Constants.lua:1628` (`ExtraStunSeconds = 0.6`) vs `:1668` (`HitStunDuration = 0.6`), applied via
`math.max` at `CombatSystem.lua:977` then `:1035`. Identical values, max not addition, so the
Normal finisher is mechanically a Basic3 with more damage. Holding jump for the Uppercut is
unconditionally correct — a variant choice with no choice in it.

**D6 — Secondary's Basic windups are below the reaction floor.**
`Constants.lua:2414, 2429, 2442` — 0.06 / 0.07 / 0.08 s.
Primary was playtest-retuned from 0.08 to 0.31 with the note that all three stages then "read as
landing on-swing". Secondary never received that pass. A 60 ms windup over a network against a
30 Hz sampler is a de facto true unparryable, which `combat-philosophy.md` Balance Principle 3
prohibits without a telegraphed cost. It also makes Feint (legal only inside windup) nonexistent
on that weapon.

### 3.3 Leaks and lifecycle

**D7 — Training bot leaks if its owner leaves within the 3 s respawn window.**
`TrainingBotSystem.lua:251-283`. `onTrainingBotKilled` clears `botAIStates[botModel]` at `:253`
*before* scheduling the respawn; the delayed callback's first statement returns early if the owner
has left (`:265`), skipping `DespawnTrainingBot` at `:269`; and `onPlayerRemoving` (`:285`)
iterates `botAIStates`, which no longer contains the entry. Permanently leaked: the Model,
`botStates`, `botsByOwner` (retaining a departed `Player` as a key), `BotAnimator.tracksByBot`, and
— if the bot died blocking — a per-bot `RunService.Heartbeat` connection (`BotAnimator.lua:161`)
that runs forever. **Fix is a one-line reorder.**

**D8 — `recentOpponents` retains departed players.**
`CombatSystem.lua:2906-2926` clears `combatStates`, rate-limiter buckets, notifiers,
`characterToPlayer`, lock-on and suspended references — but never scrubs the departing player from
*other* players' `recentOpponents`. Bounded to 4 per player and functionally harmless, but it never
releases on a high-churn server. ~4 lines, same shape as `clearLockOnReferencesTo`.

## 4. Performance baseline (counted; projections flagged)

### 4.1 Measurement blockers — fix before profiling anything

`Constants.lua:2199` — `DebugHitboxes = true`. `HitboxResolver.renderDebugHitbox` creates one Part
per sweep sub-pose per sample: 3 substeps × ~7 samples = **21 Instance.new + 21 Debris:AddItem per
swing** (~48/sec per attacker) in Studio. Live servers are safe via the `IsStudio()` double-gate;
Studio profiles are not.

`Constants.lua:48, 51` — Logger `Enabled = true`, `Level = "Debug"`, all 23 scopes on. ~8 log
emissions per landed hit, each sorting and `string.format("%q", …)`-ing its field table.

Capture two baselines (logging Off and Debug); the delta quantifies the logger overhead directly.

### 4.2 Network — the budget is `~4 calls/sec/player`

**Counted, 1v1 sustained M1 pressure: ≈13.2 downstream calls/sec/player — 3.3× budget.**
Largest single contributor is `VitalsUpdated` firing at 2.0/sec purely from passive posture regen
(`CombatSystem.lua:2638`), which is deterministic and should be replicated as a ramp, not as state.

Upstream *is* policed by three `RateLimiter` instances (`CombatSystem.lua:221-223`). **Downstream
has no limiter, no batcher, no coalescer.** That asymmetry is the structural finding.

`Combat_ParryWindowOpened` (`CombatSystem.lua:425`) is an unfiltered `FireAllClients` with no
distance, visibility or relevance filter. `ParryCooldownSeconds = 1.2` caps one combatant at 0.83
arms/sec, broadcast to every connected client. *Projected:* ~16.6 inbound calls/sec/client at 30
players, ~29 at 50 — 4× to 7× the entire budget from one remote.

### 4.3 Hit detection

`getSwingCandidates` (`CombatSystem.lua:634-639`) runs `GetPartBoundsInRadius` over 20 studs with
**`MaxParts` never set** (verified: zero occurrences in the file) and the only filter being "exclude
the attacker's own character". Every map part, terrain voxel and prop in the sphere is returned,
then string-compared against `"HumanoidRootPart"`. `HitboxResolver.lua:194` *does* set `MaxParts` —
the discipline exists one module over and was not applied here. Called fresh on every sample:
~7 samples/swing × 2.27 swings/sec = **~16 uncapped radius queries/sec per attacker**.

*Projected* at ~1,000 parts in a decorated arena: ~480k returned-part iterations/sec at 30
attackers. **This is the least certain assumption in the audit and the highest-value thing to
measure** — in an empty baseplate it profiles as free, which is exactly why the A/B in §7 must run
in a real map.

**Allocation churn:** ~22 heap objects per hitbox sample × 7 samples = **~154 per swing**
(fresh `OverlapParams`, `poses`, `priorityByModel`, `overlapped`, `seenThisSample`, a capturing
sort comparator, plus fresh arrays from `GetAliveDummies`/`GetOwnedAliveBots`). All mechanically
poolable to ~15/swing with no behavioural change.

### 4.4 Where the cost is *not*

`onHeartbeat` (`CombatSystem.lua:2552-2659`) is **O(P × MaxTrackedOpponents) = O(4P)** — linear,
constant-bounded, no O(n²) anywhere. ~10-11 engine boundary crossings per player per tick.
*Projected* ~0.5-0.9 % of frame budget at 30-50 players. **Do not optimize this.** The genuinely
O(P) scans are event-driven only (death, leave, air-tech), never per-tick.

Server scheduler discipline is clean: every `task.delay`/`task.spawn` is bounded and owned, no
orphaned coroutines, and every per-tick system correctly piggybacks the single Heartbeat via
`OnHeartbeatTick` rather than opening its own. VFX pooling via `FXPool` is correctly used
everywhere it should be. These need no work.

## 5. Structural findings

### 5.1 The combatant model is O(kinds²)

`CombatTypes.lua:284` (`CombatState`), `:462` (`DummyState`), `:486` (`BotState`) are three
hand-mirrored types sharing ~17 identically-named fields, with **four** separate hit-resolution
functions covering four of nine attacker→target pairings (`CombatSystem.lua:867`,
`DummyCombat.lua:274`, `BotCombat.lua:377`, `:518`), each 150-230 lines independently
re-implementing classify → compute → apply → feedback → posture-break → death.

`HitResolution.lua` already extracted the *pure math* from all four — the right call. The
*orchestration* is still duplicated four times.

The proof the wrong abstraction is in place is `AirComboTarget` (`CombatTypes.lua:543`): a
hand-written closure adapter, built per hit at two call sites, existing solely to let one state
machine work against two combatant shapes. That is the `Combatant` interface, discovered by
accident and scoped to one feature.

`CombatVitalsState` (`CombatTypes.lua:89`) is *already* shared-shaped across all three — evidence
the decomposition is natural rather than invented.

**Consequence:** each new combatant kind costs a mirrored state type plus a resolver per pairing.
The first real PvE enemy is where this bites.

### 5.2 The Hooks pattern has reached its limit

The `require` graph is genuinely acyclic (`CombatSystem` → siblings, never back). The **call graph
is cyclic**, and the Hooks table is what hides the cycle from tooling:

```
CombatSystem.onBotSwingHitCandidate → BotCombat.ResolveHitFromBotAgainstPlayer
  → hooks.TriggerPlayerPostureBreak → CombatSystem.triggerPostureBreak → sendFeedback
```

Three symptoms: `local hooks: Hooks? = nil` guarded by runtime `assert`s (`AirCombo.lua:397, 497`)
means a registration-order mistake is a mid-fight production crash, not a compile error; the 12
hooks are concrete pointers to private locals, not an interface either side owns; and the count
grew monotonically (Dummy 2 → Bot 3 → AirCombo 7). The next sibling would need nearly all of them.

**The `Server/Combat/` sibling folder is the right continued vector. The Hooks mechanism should be
retired before an ability system doubles down on it.** Two extractions eliminate all 12:
`CombatChannel` (remotes + senders — 9 of the 12) and `CombatantRegistry` (`combatStates`,
`characterToPlayer`, the reverse scans).

### 5.3 `Constants.lua` at 2,622 lines — three distinct problems, only one is size

1. **It holds content, not tunables.** `CharacterCreation` (207 lines), `Weapons` (231 lines of
   full attack definitions), a flat `AnimationIds` map. At 200 weapons that table alone is ~23,000
   lines.
2. **It replicates server-only secrets.** `Debug.DevMenu.AuthorizedUserIds` (`:94`) — the admin
   whitelist — plus all five DataStore names (`:539, 907, 908, 936, 941`) sit in `ReplicatedStorage`.
   Not privilege escalation (`DevMenuSystem` re-checks server-side, clients cannot reach
   DataStoreService), but gratuitous disclosure of exactly which accounts are worth attacking.
3. **It is mutated at runtime.** `HitboxTuning.lua:5-20` states it outright: mutating a field takes
   effect on the next swing, and even on an in-flight one. `Constants` is not constant.

The correct split is by **replication boundary and mutability**, via a facade that re-exports
existing keys so no call site changes and no step has a "both copies exist" window.

### 5.4 A second monolith is forming

`DevMenuSystem.lua` — 1,340 lines, **34 RemoteFunctions** (a larger remote surface than all of
combat), requires six Systems plus two tuning modules (highest fan-out in the repo), spans five
unrelated domains, and contributes ~250 of `Types.lua`'s 753 lines as dev-tool RPC shapes in the
shared game type file.

It is also the one module that breaks `CombatSystem.lua:25-26`'s documented invariant that
`Server/Combat/` siblings are "required only here" — verified: `DevMenuSystem.lua:39` requires
`Combat.HitboxTuning`. `HitboxTuning` is a dev tool that writes to combat data, not a combat
sibling; it belongs beside `FlightTuning` outside `Server/Combat/`.

### 5.5 Movement's model is a dead end for the stated goals

All movement is `Humanoid.WalkSpeed` multipliers through one 8-tier resolver
(`Movement.lua:159-224`). `WalkSpeed` is not a velocity — it is a target-speed parameter of a
closed-source controller. Four consequences, each individually fatal to the requested slide:

- You cannot move in a direction the player is not already holding (`handleDashRequest`'s own
  comment concedes this).
- You cannot carry momentum across a state change — every tier is `base × multiplier` recomputed
  from scratch, so slide exit steps 36 → 18 in one frame.
- **Slope is invisible by construction.** The Humanoid controller normalizes commanded speed across
  slopes. Downhill acceleration is a change in speed the player did not command, so no multiplier
  of `WalkSpeed` can express it. This is not a tuning gap.
- Acceleration/deceleration curves belong to the engine and are un-tunable.

Slide today is `SlideSpeedMultiplier = 2.0` for 0.35 s plus one animation clip — a reskinned Dash
with a worse cooldown. It teaches nothing about the world.

**Recommended replacement:** keep the Humanoid; add a `LinearVelocity` constraint on
`HumanoidRootPart`, engaged only while a traversal state owns the body, with `WalkSpeed` driven to
0 for exactly that window. Precedent already exists in-repo — `FlightPhysics.lua` does exactly this,
including the finite-`MaxForce` reasoning. The physics model itself belongs in a pure
`Shared/SlideMath.lua` (mirroring the existing `FlightMath.lua` split) so it is TestEZ-coverable
headlessly; without that split, no slide behaviour is testable and every tuning change is a live
playtest gamble.

### 5.6 Ability authoring has hard prerequisites

The entry point already exists and is well shaped: `HitboxTuning` performs live in-memory mutation
of attack definitions through a whitelist-gated Fusion dev menu. Its own header names the missing
piece — *"this module never writes to disk... meant to be copied BY HAND back into Constants.lua."*
`ACTION_GATES` (`CombatSystem.lua:1646`) is already a data-driven gate table whose header
explicitly anticipates abilities. `Types.HitboxAttackDefinition` is already a serializable record.

The framework is a **generalization of what exists** — persistence plus a richer schema — not a new
system.

**But it will become a competing combat system unless gating, hitboxes and damage are physically
unavailable to it.** `ActionGate` and a unified `DamagePipeline` must exist *first*, as required
dependencies it does not own. Otherwise it grows its own copies of all three, which is the outcome
this milestone exists to prevent.

## 7. Instrumentation plan

The milestone requires before/after performance findings. Static analysis supplies counts, not the
"before". This converts them.

**Step 0 (required):** set `DebugHitboxes = false`; capture two baselines, logging `Off` and
`Debug`. The delta is itself a deliverable.

**Step 1 — MicroProfiler labels:** `CS/Heartbeat`, `CS/PlayerLoop`, `CS/GetCandidates`,
`CS/RadiusQuery` (the query call alone, separated from the Luau loop), `HR/Update`, `HR/Sample`,
`HR/BoxQuery`, `RC/Enter`, `RC/Exit`, `RC/Ownership`, `Bot/DecisionTick`; client
`CC/LockOnRender`, `CA/LocomotionTick`, `FX/HitFlash`.

**Step 2 — counters** (Studio-only, gated like `Logger`), dumped per second:
`remotes.out.<name>` at all 13 fire sites, `remotes.out.total / playerCount` (**the headline budget
number**), `remotes.in.<name>`, `ratelimit.drops.<bucket>`, `hitbox.samples`,
`hitbox.radiusQueryParts` (**the least certain projection in this audit**), `hitbox.boxQueryParts`,
`ragdoll.instancesCreated`, `ragdoll.ownershipCalls`.

**Step 3 — engine metrics** sampled 1 Hz to CSV: `HeartbeatTimeMs`, `PhysicsStepTimeMs`,
`GetTotalMemoryUsageMb`, the `Script` and `Instances` memory tags, `DataSendKbps`,
`DataReceiveKbps`, client `RenderStepTimeMs`.

**Step 4 — load scenarios,** 120 s each: S0 idle · S1 1v1 sustained · **S2 the same 1v1 in a
decorated map vs. a bare baseplate** (the decisive `getSwingCandidates` A/B — do not skip the
control) · S3 ten-player scrum · **S4 thirty players in three distant scrums** (proves or refutes
the broadcast finding: if `ParryWindowOpened` scales with 30 rather than 10, it is confirmed) ·
S5 S4 plus continuous ragdolls · **S6 sixty-minute soak with churn** (leak detection — any positive
slope in the memory tags is a leak).

**Exit criteria:** `remotes.out.total / playerCount ≤ 4/sec` in S1 and S4 · `CS/Heartbeat` ≤ 2 ms
at 30 players · `hitbox.radiusQueryParts` ≤ 2× player count · flat memory across S6 ·
**every `Tests/Combat/*.spec.lua` still green** — the existing suite is the correctness net for
every optimization above, and none may cost a passing test.

### Deliberately not done

- **Primary's Basic string violates the `Cooldown >= Windup+Active+Recovery` invariant** documented
  in `Constants.Combat.Weapons`' header (Basic1 totals 0.67 against a 0.44 cooldown). This
  pre-dates this milestone — it is a side effect of the 0.08 → 0.31 playtest retune, which raised
  the timeline without raising the cooldown. It is **not** a live bug, because `attackEndsAt` (the
  commitment lock) is the actually-binding gate, but the documented invariant is stale and
  `PredictionMirror` asserts the opposite relationship. Left alone: "fixing" it would slow the M1
  string by ~50%, far outside a defect pass, and Primary's 0.31 was explicitly playtest-confirmed.
  Pick one invariant, document it once, and assert it — as its own decision.
- **`DaggerHeavy1/2` windups (0.14/0.15)** are also low. The audited item was the Basic string;
  raising Heavy is a further balance call, not a defect fix.
- **Disarm** (`HitResolution.ShouldDisarm`, `return false and (...)`) was reported by the combat
