# Post-Combat-Rewrite Architecture Audit

**Date:** 2026-08-19
**Scope:** current source on `progression-spine`, read fresh — not a patch of
[`2026-08-audit.md`](2026-08-audit.md), which was written against a combat system
(`CombatSystem.lua`, `CombatClient.lua`, `BotCombat.lua`, `HitboxResolver.lua`, `AirCombo.lua`,
`ActionGate`) that no longer exists. That document is annotated as superseded and left otherwise
untouched — see its own new header line.
**Method:** direct reading of the current combat stack, shared-module call sites, `BootManifest.lua`
vs. `Main.server.lua`/`Main.client.lua`, and every progression System's actual body (not its filename
or its own header's claims). Every finding below was confirmed by reading the cited file/line, and a
"wired" claim was checked with a `grep -rn "require(...)" src/` inbound-count from outside the
module's own folder, per `CLAUDE.md`'s own reachability bar. Nothing here was fixed while producing
it — this is a read-only report for triage.

---

## 1. Executive summary

The four-layer combat rebuild (`HitboxEngine → DefenseSystem → DamageSystem → AttackRequestSystem`,
`GrabSystem` as a documented sibling) is **real, complete, and clean**. Every layer boundary described
in `CLAUDE.md`'s "Combat stack layering" section was checked against the actual `Init()`/`Step()`
bodies and holds exactly as documented: each layer's only reach into the one below is the single named
seam (`DefenseSystem.DrainGuard`, `DamageSystem.OnApplied` → `GrabSystem`, the three `CanAttack` gates
`AttackRequestSystem.Throw` asks). No sideways or upward layer violation was found. `BootManifest.lua`
and `Main.server.lua`/`Main.client.lua` are in sync — no drift, no orphaned System, no undeclared
remote. `DebugDummySystem` and the `ObjectStunEditor` dead-resolver notice are both genuinely wired as
the brief described; that part of the prior session's work checks out.

The one substantive gap found is **inconsistent adoption of `Shared/RemoteHandler.lua`** (§2) — the
module that exists specifically to stop a thrown Lua error from crossing a `RemoteFunction` boundary.
Two Systems use it correctly, one has an explicitly documented reason not to, and at least five others
either hand-roll the identical pcall wrapper it was built to replace or have no pcall boundary on
`OnServerInvoke` at all.

Progression systems split cleanly into two groups, verified by reading bodies, not filenames (§3):
`ArtSystem`, `TierSystem`, `QiSystem`, `BountySystem`, and `RivalrySystem` are real, non-trivial
implementations. `FactionManager`, `BloodlineManager`, `BloodlineSystem`, `ProgressionSystem`,
`AchievementSystem`, `QiDeviationSystem`, `AbsorbSystem`, `RewardSystem`, `AwakeningSystem`,
`TerritorySystem`, and `WorldSystem` are genuinely still stubs (18–33 lines each, empty `Init()`) —
this matches `BootManifest.lua`'s own "PLANNED SYSTEMS" framing exactly, so that framing is currently
honest, not aspirational.

One scalability note worth flagging early for later content growth (§4): the hand-authored weapon
moveset (`DefaultMoveRegistry.lua`) is a closed enumeration over a hardcoded 3-name standalone-attack
union and whatever `CombatConstants.Weapons` lists — it is not itself the scalable path to 200 weapons,
and shouldn't become one. The scalable path already exists and already works (`MoveRegistryManager` +
the Move Editor's DataStore-backed authoring UI, which is how `ArtSystem` gets its content today) —
this is a note to keep new weapon content flowing through that pipeline, not a defect.

## 2. `RemoteHandler.lua` adoption is inconsistent

**RESOLVED 2026-09-27** — re-verified against current source. All six real gaps this section names
(`ArtSystem`, `RivalrySystem`, `BountySystem`, `SettingsSystem`, `CharacterSheetSystem`,
`CharacterCreationSystem`) are now migrated to `RemoteHandler.WrapInvoke`. `ServerHopSystem` remains
unwrapped, but that is the documented, intentional exemption CLAUDE.md itself names (a
`(boolean, string?)` multi-return `WrapInvoke`'s single-`Result` generic cannot express) -- not an
open gap. Left below for the historical record of what the gap looked like and why it mattered; do
not re-file it as open without re-checking the call sites first.

**Severity:** Medium
**Category:** Consistency / Technical Debt
**Location:** `src/ReplicatedStorage/Shared/RemoteHandler.lua` (the module); call sites below.

### Evidence

`RemoteHandler.lua`'s own header names exactly what it was extracted to replace: *"The same shape
DevMenuSystem.wrapHandler, MoveEditorSystem.wrapHandler, and BugReportSystem.Init's inline pcall each
hand-wrote independently."* Checking all three against current source:

- `DevMenuSystem.lua:1347` — migrated. Every entry in its `REMOTE_HANDLERS` table is wrapped via
  `RemoteHandler.WrapInvoke(logger, spec.Name, DEV_MENU_INTERNAL_ERROR_RESULT, spec.Handler)`.
- `BugReportSystem.lua:792` — migrated. `submitRemote.OnServerInvoke = RemoteHandler.WrapInvoke(...)`.
- `MoveEditorSystem.lua:114-123` — **not migrated, but deliberately so.** Its own header (lines 11-13)
  states: *"wrapHandler stays a local copy ... since generalizing that one too was ruled out during the
  Network-module design pass -- see Shared/RemoteHandler.lua's own header for the module that WAS
  extracted for that shape."* This is a documented exception, not a gap — noted here only so it isn't
  mistaken for one on a future pass.

Two classes of real gap exist beyond those three, neither documented as intentional:

**(a) A fourth hand-rolled duplicate of the exact pattern, not mentioned anywhere as ruled out.**
`CharacterCreationSystem.lua:588-598` and `:603-610` each inline the identical
`pcall(handler, player, ...) / log / return fallback` shape `RemoteHandler.WrapInvoke` exists to
collapse, on `GetOnboardingState` and `Finalize` — the two remotes gating every player's first
character creation. Nothing in the file explains why this one wasn't migrated alongside DevMenuSystem
and BugReportSystem; it reads as simply missed.

**(b) `OnServerInvoke` handlers with no pcall boundary at all** — a thrown error inside the handler
currently propagates directly across the remote to the client:
- `ArtSystem.lua:381,384,390` — `GetArtCatalogue`, `UnlockArt`, `EquipArt` (progression-critical:
  unlock/equip is the entire path an Art becomes usable).
- `RivalrySystem.lua:175,195` — `GetTopRivals`, `GetStandingAgainst`.
- `BountySystem.lua:416` — `GetActiveBounties`.
- `ServerHopSystem.lua:51` — `RequestTeleport`.
- `SettingsSystem.lua`, `CharacterSheetSystem.lua:116` — `GetSettings`, `GetSheet`.

None of these five is exotic: each is a straightforward request/response handler doing table lookups
and profile reads, exactly the shape `RemoteHandler.WrapInvoke`'s generic signature
`(Player, Args...) -> Result` was built for. `ArtSystem`/`RivalrySystem`/`BountySystem`/`SettingsSystem`
all already `require(ReplicatedStorage.Shared.RateLimiter)` and use it correctly on the same handlers —
the rate-limiter half of "harden a remote" is universal in this codebase; only the pcall half is spotty.

### Why it matters

A single uncaught error inside, say, `handleEquipArt` (a bad index into `ArtTreeManager`'s registry, a
nil profile mid-transform) doesn't just fail that one request — depending on the Roblox runtime's
handling of an erroring `OnServerInvoke`, the client-side `InvokeServer` call can hang or throw in a way
`Client/Network/RemoteInvoker.lua`'s `Invoke`/`InvokeAndReport` wrapping wasn't written to expect
gracefully-degrading errors from (`RemoteInvoker` assumes a clean `(ok, Result...)` from a server that
already turned its own errors into typed results). It's also an availability gap with no server-side
trace: today an error in `handleEquipArt` produces no `logger:error` call anywhere, because nothing on
that path calls `pcall` at all — a production incident here is invisible to the Live Console.

### Recommendation

Migrate the five no-pcall call sites to `RemoteHandler.WrapInvoke`, matching each System's own
`Types.*Result` shape as `errorResult` (they already all return a `{ Success, Reason }`-or-similar
shape on every other branch, so the fallback value is a one-line addition, not a redesign). Migrate
`CharacterCreationSystem`'s two hand-rolled wrappers the same way DevMenuSystem's were — they are
byte-for-byte the pattern `RemoteHandler` replaces and there's no documented reason (unlike
`MoveEditorSystem`) that this one needed to stay local.

### Migration plan

1. `CharacterCreationSystem.lua`: replace the two inline `function(player, ...) local ok, r = pcall(...)`
   blocks with `RemoteHandler.WrapInvoke(logger, "GetOnboardingState", { NeedsOnboarding = false }, handleGetOnboardingState)`
   and the equivalent for `Finalize`. Requires adding `local RemoteHandler = require(...)`.
2. `ArtSystem.lua`, `RivalrySystem.lua`, `BountySystem.lua`, `ServerHopSystem.lua`, `SettingsSystem.lua`,
   `CharacterSheetSystem.lua`: wrap each `OnServerInvoke` assignment the same way, one call site each.
   Every one of these already computes a typed failure value on its validation branches (e.g. `{
   Success = false, Reason = "InvalidArtId" }`), so the `errorResult` argument is just that same shape
   with an `"InternalError"`/empty-collection fallback.
3. No test currently asserts pcall-safety at these call sites (only `BugReportSystem`/`DevMenuSystem`
   are exercised that way, if at all) — worth a shared spec pattern once the migration lands, rather than
   six near-identical ad hoc ones.

### Tradeoffs

Migrating costs one `require` line and one wrapper call per site — genuinely cheap. The only reason
this wasn't already done everywhere is that `RemoteHandler.lua` is newer than several of these Systems
and nothing enforces the pattern at review time (no lint rule, no spec). That absence of an enforcement
mechanism is itself worth a line in the toolchain notes once this migration lands, so the next new
`OnServerInvoke` doesn't reopen the same gap a sixth time.

### Long-term impact

Left alone, this is exactly the kind of gap that compounds with content growth: every new progression
System (Bloodline, Territory, World, once they stop being stubs) will each independently decide whether
to wrap its own remotes, and without a single answer already modeled everywhere, some fraction won't.

## 4. Combat stack cross-check: no boundary violations found

**Severity:** Informational (negative finding — explicitly checked, not assumed)
**Category:** Architecture
**Location:** `src/ServerScriptService/Server/Combat/**`

Checked each layer's actual `require()` list and call sites against `CLAUDE.md`'s stated boundary
("each layer is ignorant of the one above it and gets exactly one narrow upward seam into the layer
below"):

- `HitboxEngine.lua` — requires nothing above it in the stack. Confirmed: it has no knowledge of
  `DefenseSystem`/`DamageSystem`/players/damage/blocking anywhere in the file.
- `DefenseSystem.lua` — requires `HitboxEngine` only (`OnHit` subscription, `CancelAttack`,
  `GetCombatantId`). The one seam back up is `DrainGuard`, called by `DamageSystem`, exactly as
  documented.
- `DamageSystem.lua` — requires `DefenseSystem` (`OnResolved`) and `HitboxEngine` (`GetCombatantId`,
  `CancelAttack`) and `AttackCatalog` (a sibling lookup table, not a layer). No registry of its own, as
  its header states and the code confirms (state is derivable per-call, not stored per-combatant).
- `AttackRequestSystem.lua` — requires all three layers below plus `GrabSystem` (documented sibling,
  read as a third `CanAttack`-shaped gate) plus `ArtSystem` (`Server/Systems/ArtSystem.lua:107`) and
  `AdminConfig`. The `ArtSystem` dependency is a **new, previously-unaudited edge** — it is not one of
  the four documented layers, so it's worth stating explicitly why it isn't a violation: `ArtSystem`
  does not require anything under `Server/Combat/` (checked — `grep -rn "require(.*Combat" src/Server*/
  Server/Systems src/Server*/Server/Managers` returns only `DevMenuSystem`, `DebugDummySystem`,
  `MoveEditorSystem`, `RunSystem`, and `ArtTreeManager`, none of which is `ArtSystem` itself), so the
  dependency is one-directional and the combat stack's require graph stays acyclic. Reaching into a
  progression System to resolve "what is equipped" and "can afford the cost" from the topmost combat
  layer is the same shape as an inventory lookup, not a fifth combat layer — but it is now
  `AttackRequestSystem`'s fourth external dependency (three combat layers + one progression System), and
  if a second progression System (say, a future `StatusEffectSystem` modifying attack cost) needs the
  same kind of read, that's the point to reconsider whether the seam should be narrowed to an interface
  `AttackRequestSystem` owns rather than a growing list of direct `require`s to progression Systems.
- `GrabSystem.lua` — requires `DamageSystem` only (`OnApplied`), confirmed sibling shape, not stacked.

No sideways reach (e.g. `HitboxEngine` reading `DefenseSystem` state, or `DefenseSystem` reading
`DamageSystem`) was found anywhere in the four files. This is a clean rebuild.

## 6. Scalability note: `DefaultMoveRegistry.lua` is a closed enumeration, not the growth path

**Severity:** Low (note for later, not a current defect)
**Category:** Scalability
**Location:** `src/ServerScriptService/Server/Combat/DefaultMoveRegistry.lua`

`DefaultMoveRegistry.lua` hand-enumerates exactly two categories of content: per-weapon
Basic/Heavy/Finisher stages read live off `CombatConstants.Weapons[...]` (`WeaponStageCategory` is a
closed 3-member union, `weaponStageMoveId`/`enumerateDescriptors`), and a hardcoded 3-name standalone
set (`STANDALONE_ATTACK_NAMES: { StandaloneName } = { "DashPunch", "DashHit", "AirSlam" }`, itself a
closed type union). Its own header is explicit that this is deliberate: it is the "Default" (formerly
DevMenu Tuning tab) live-tunable projection of a small, hand-authored baseline moveset, distinct from
`MoveRegistryManager`'s DataStore-backed custom-move registry that `ArtSystem` and the Move Editor's
"Save" path actually use for real content growth.

This is not a defect today — `AttackCatalog.Get`'s own resolution order (`MoveRegistryManager.Get`
first, `DefaultMoveRegistry.Get` as fallback) already means every *new* weapon or Art added through the
Move Editor's authoring UI goes through the scalable, data-driven path and never touches this file. The
risk is purely a future-developer-experience one: `STANDALONE_ATTACK_NAMES` and `WeaponStageCategory`
being closed unions means a well-intentioned future contributor extending "the two starter weapons"
pattern by hand (rather than through the Move Editor) will hit a wall that requires editing this file's
type unions, `CombatConstants.Weapons`, and the enumeration logic together — three coordinated edits for
one new hardcoded weapon, which is exactly the kind of friction that should route people back to the
already-built scalable path instead. No action needed now; worth a one-line comment pointer in this
file the day a second contributor reaches for it to add weapon #3.
